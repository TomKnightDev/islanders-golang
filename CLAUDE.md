# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Islanders is a small multiplayer top-down 2D game. One Go module (`github.com/tomknightdev/islanders-golang`) holds three packages:

- `server/`: a websocket game server (gorilla/websocket). It owns world generation, the player registry, every character's movement and jobs, and the enemies at camps. The old wandering NPCs were removed and are in git history (`server/npc.go`).
- `client/`: a desktop client built on Ebiten v2, with imgui for menus and chat. It needs **cgo/GCC** to build.
- `resources/`: shared message types, tile constants and the `WorldMap` struct. Both sides import it.

Game design, the planned gathering/crafting loop and the phase plan live in `docs/DESIGN.md`. Read it before working on gameplay.

## Commands

```bash
make build          # builds bin/server and bin/client
make run-server     # go run ./server/ -addr 0.0.0.0:8285 -dev (override with SERVER_ADDR=...)
make run-client     # go run ./client/
make build-client-windows   # bin/windows/Islanders.exe; needs brew install mingw-w64. CI also builds it and uploads it as the Islanders-windows artifact
go build ./server/  # what CI runs, plus the Windows client build
go vet ./...
go test ./server/ ./resources/   # what CI runs; client/client_test.go is commented out
go test ./client -run TestName   # single test
```

Without `-addr`, the server binds to `<outbound IP>:8285`. The client's main menu has two buttons: **Play online** connects to the production server and **Play locally** to `localhost:8285` (both addresses are constants in `client/gui/mainmenu.go`). `make run-server` listens on all interfaces, so Play locally reaches it.

## Deployment

Every push to `master` triggers `.github/workflows/server.yml`. It builds the server, pushes `ghcr.io/tomknightdev/islanders-server:master` and redeploys the container on a DigitalOcean droplet over SSH. In practice, merging to master deploys to production. The Dockerfile copies only `server/` and `resources/`, so the server must never import anything from `client/`.

## Architecture

**Protocol.** Every message is a JSON `resources.Message{MessageType, Contents, ClientId}`. `Contents` is an `interface{}`, so the receiving side gets `map[string]interface{}` / `[]interface{}` with float64 numbers. Older handlers unpack it by hand with type assertions (for example `messageContents["pos"].([]interface{})`); if you add a field to one of those `*Contents` structs, update that manual decoding too. New code should use `resources.DecodeContents(contents, &typedStruct)` instead, as the world map already does.

**Connection flow.** The client dials `ws://<addr>/connect` and sends `ConnectRequestMessage`. For a name it hasn't seen, the server replies `ChooseClassMessage`; the client shows the class picker and sends `CreateCharacterMessage`, and the server creates the character (`World.createCharacter`, which applies the class kit from `resources.Classes`) before logging it in. A known name re-authenticates (accounts are in memory only, plaintext password, keyed by username). `World.login` on an unknown name creates a `defaultClass` character, which tests rely on. Logging in from a second connection closes the first. The server replies with `ConnectResponseMessage`, which carries the client ID, the player's position and the **entire generated world map**. It then sends `UpdateMessage`s for the other players, the player's inventory (which also carries skills, health, equipment, found places and the action list) and a snapshot of all enemies. Only after the connect response arrives does the client build the camera, `Player`, `World`, the action bar and the chat, info, inventory, equipment, actions and skills windows (`handleConnectResponse` in `client/client.go`).

**Authority.** The server owns every character. A click sends `MoveRequestMessage` with a target tile. The server pathfinds (A*, 8-directional with no corner-cutting past blocked tiles, `server/pathfind.go`); steps onto roads cost less (`stepCost`), so walkers follow roads; clicking a blocked tile walks to a free tile next to it. The server then moves the character `walkStep` pixels per 25ms tick and broadcasts `UpdateMessage` to **every** client, the owner included. The client never moves itself; `receiveUpdateMessage` applies the owner's position to `client.Player`. Characters stay in the world while their player is offline and keep walking, and other clients still see them.

**Jobs and the action list** (`server/jobs.go`). Each player has an action list (`player.actions`, up to `resources.MaxActions`) edited by `ActionCommandMessage`s (add, edit, remove, up, down, start, stop) through `World.actionCommand`, which validates that the place has been found (`player.found`, filled by `tickDiscovery`) and fits the action. While `player.running`, `tickJob` starts the first action as a `job`, a small state machine driven by two tables. `gatherKinds` (mine, chop, farm) gather from `node`s (rocks from `WorldMap.Objects`; trees and crops found on the object layer inside named forests and farms): walk to node → gather → bank → back. `recipes` (smelt, fletch) craft at a village station (`World.stations`): bank (deposit, collect input) → station → craft → bank. Each action also has a material (`ActionSpec.Material`), one of the tiers in `resources.ActionMaterials`, which sets the item, the node sprite (gathering) or input (crafting), the skill level needed and the XP. A new tier is a row in `ActionMaterials` plus its items in `resources.Items`; a new gathering or crafting action is an `ActionKind`, a row in `gatherKinds`/`recipes`, and its materials.

**Skills** (`resources/skills.go`). Twelve skills (five gathering and crafting, six combat, and Stamina), levels 1–99 on an XP curve that roughly doubles every seven levels (`XPForLevel`, `LevelForXP`); `player.xp` holds XP per skill. Every gathered item and crafted input calls `World.addXP` (which posts a level-up chat message), step times are scaled by `player.skillTicks` (`SpeedFactor`, 0.4% faster per level), and `validAction` refuses materials above the player's level or not present at the place (`Place.Materials`). Goals are checked at decision points (`amountMet`) and every tick for time goals (`queuedAction.ran` counts only running ticks); `wrapUp` banks what's carried before `finishAction` moves on, and `failAction` stops the list but keeps the action. Clicks (`World.click`) only walk, and are ignored while the list runs. Nodes belong to a place (`node.place`), are claimed when a gatherer is sent to them (one per node), turn into their spent sprite when empty (depleted rock, felled tree) and refill on a timer; tile changes go to clients as `ObjectUpdateMessage`. A node nobody can walk up to is marked `unreachable` and skipped. Backpacks and per-player bank accounts are `resources.Inventory` (slots of stacks). The bank stacks up to `resources.StackLimits`; the backpack is created with `Stacking: false`, so items take a slot each unless `resources.BackpackStackLimits` says otherwise (arrows: 50). Changes set `player.invDirty`, and the tick sends the owner an `InventoryMessage` with backpack, bank, activity, found places and the action list. All tuning values are constants at the top of `jobs.go`. Each player has their own clock (`player.ticks`, advancing every world tick, online or offline); job and action timing use it, while world timers such as rock respawns use `World.ticks`.

**Combat** (`server/combat.go`, `resources/combat.go`, `resources/equipment.go`). Enemies (`mob`) live at camp spawns (`ObjectSpawn` objects whose `Variant` is a `resources.Enemies` ID), wander from `tickMobs` on the world clock, and are sent to clients as `ServerEntityUpdateMessage` entries (`Gone` when dead). Fighting is a job like the others: `atBankForFight` (rest, take food) → camp → `seekEnemy` (claims one enemy) → `tickFight`. While a mob is being fought, both sides' attacks and its movement run inside the fighter's `tickFight`, on the fighter's clock. `defeat` empties the backpack and returns the player to the spawn. Fighting styles (melee, ranged, magic, necromancy) come from the weapon: `Bonuses.Style()` and `Bonuses.Skills()` pick the skills used, bows and staves reach `castRange`, and a staff's `Drain` heals the wielder. Equipment lives in `player.equipment` and changes through `EquipCommandMessage` → `World.equipCommand`; bonuses come from `resources.EquipmentBonuses`. Health is `player.health` (max from Hitpoints), sent to everyone in `UpdateMessage` and to the owner in `InventoryMessage`.

**Fight panel.** `sendFightState` (each tick) tells a fighter when they start or stop fighting an enemy, and `fightEvent` reports every attack by either side, both as `FightMessage` to the fighter only. The client's `gui.FightPanel` animates from the latest event (lunge, flash, floating damage) and lingers briefly after the fight ends.

**Items and quality** (`resources/items.go`, `resources/quality.go`, `server/items.go`). A `resources.Stack` carries `Quality`, `Damage` and `ID`. Materials stack and average their quality (`Inventory.AddStack`); gear and tools (`resources.IsPiece`) are stacks of one with their own ID from `World.newPiece`. Use `World.give` to create items, `moveItems`/`Inventory.Take`/`AddStack` to move them (never `Remove` + `Add`, which loses quality), and `Inventory.Add` only where quality doesn't matter (it uses `DefaultQuality`). Gear bonuses scale with quality in `EquipmentBonuses`; tools live on the belt (`resources.ToolSlots`, `ActionTool`) and set speed (`player.stepTicks`) and gathered or crafted quality (`GatheredQuality`, `CraftedQuality`).

**Economy** (`server/economy.go`, `resources/economy.go`). `player.coins` lives with the bank account. Item values are `resources.Values`; stores are `World.stores` (one per village, by name), each with a `demand` multiplier per item that `store.buy` lowers and `tickStores` recovers each minute. Selling is a job (`ActionSell`, whose `Material` is any item kind): bank → `collectForSale` → `stateWalkToStore` → `stateSelling` → `sellCarried`. Its goal, like fighting's, counts what the action did (`queuedAction.count`, `resources.CountsProgress`). The Shop window sends `ShopCommandMessage` (view or buy) and gets `StoreMessage` back. The inn fee is taken in `startRelaxing`, falling back to the slower stable.

**Stamina** (`server/stamina.go`). `player.stamina` drops with each step of work (`spendStamina`, which also trains Stamina). `exhausted` is checked at the start of each swing, craft step and attack; at zero it calls `goToInn`, which releases the node or enemy and sets the job to `stateWalkToInn` → `stateRelaxing`. When rested the job is dropped (the action stays first in the list), so `tickJob` starts it again. `queuedAction.ran` doesn't count inn time.

**Routes.** `World.sendPath` sends a player their own path (`PathMessage`) whenever its destination changes; the client trims it as the character walks and draws it after the camera image.

**Window layout.** `client/gui/layout.go`: `placeWindow` pins a window to a screen position and corner for its first few frames each session (overriding `imgui.ini`), then leaves it movable. Skills sits under Info via `infoBottom`; the picker opens beside Actions via `actionsLeft`.

**Hover tooltips.** `gui.Hover` looks up the object-layer tile under the mouse in `resources.ObjectInfo` and adds context from `WorldMap.Places`; the inventory window shows `resources.ItemDescriptions` on hover. New objects and items need an entry there.

**Action bar.** Every activity change or new timed step (each mining swing, smelt or walk) calls `startAction`, which sends the owner the action's length and elapsed time in the `InventoryMessage`. The client's `gui.ActionBar` animates the green fill locally from that, so the server doesn't send progress every tick. Open-ended activities (idle, waiting, bank full) have length 0 and show an empty bar; idle hides it.

**Sending state to writers.** A message handed to `session.push` is encoded later on the writer goroutine, so it must not share memory the world keeps changing. Use `Inventory.Clone()` and `WorldMap.Clone()` when putting live state into a message.

**Entity IDs.** Players get `0, 1, 2…` from `World.nextID`; enemies get 20000+ (`mobIDBase`). Both are `NetworkPlayer`s on the client, in `client.NetworkPlayers` / `g.Entities`: players arrive in `UpdateMessage`, enemies in `ServerEntityUpdateMessage` (a `Gone` entry removes one until it respawns).

**World.** `server/worldgen.go` generates a 160×160 island from a fixed seed (`worldSeed`), so the map is identical on every start; changing the generator or seed moves everything players know. Pipeline: island elevation from value noise with a radial falloff → rivers walked downhill from highlands → terrain painted from elevation bands → villages, then mines, farms and camps (mines and camps ranked harder with distance from the spawn) placed on the mainland away from water → roads to all of them (weighted A*, bridges over rivers, never through crops) → forests and decoration → the largest forests named → a reachability check from the spawn. Three row-major layers (`Data[y*width+x]`): ground (opaque; water blocks), objects (anything non-zero blocks) and decor (never blocks). Interactive objects (and invisible enemy spawns) are listed in `WorldMap.Objects`, named places with what can be gathered or fought there in `WorldMap.Places`, and the spawn in `WorldMap.SpawnX/Y`. Copper and mithril rocks are tinted copies of the iron rock (`resources.TintedTiles`, gids past the end of the sheet). Tiles are 8px; values are Tiled-style gids into `environments.png` (atlas column `(gid-1)%16`, row `(gid-1)/16`). The client's `World` pre-renders all layers into one image and draws place names over the map. To look at the island without running the game, render `generateWorld(worldSeed)` to a PNG from a throwaway test.

**Collision** is `WorldMap.TilePassable` / `BoxPassable` in `resources`, used by server pathfinding. A ground tile blocks if `IsPassable` says so; any non-empty object tile blocks.

**Rendering.** Every drawable entity shares one `ebiten-camera` instance and draws onto `cam.Surface` (`World.Draw` clears it and draws the pre-rendered map first). `Game.Draw` then blits the surface to the screen once and draws, in screen space so they stay sharp at any zoom, the player's route, place names, character names and health bars (the `entities.Labeled` interface), then the GUI. The camera follows the player unless they've dragged the map (`Player.FollowCam`). All GUI windows share one imgui `renderer.Manager`; they're opened between `BeginFrame` and `EndFrame` in `Game.Update`, with the 22px UI font (`uiFontSize`, M PLUS 1p) pushed. Don't scale imgui with `SetFontGlobalScale`/`ScaleAllSizes`; it looked blurry and was reverted in favour of the real font.

**Server concurrency.** `World` (`server/world.go`) owns all game state, and only its `Run` goroutine touches it. Connection handlers (`server/server.go`) only parse messages and submit closures with `world.Do(func(w *World){...})`; anything needing a reply passes a channel inside the closure (see login). Each connection is a `session` whose writer goroutine is the only thing writing to the socket. The world queues messages with `session.push`, which never blocks: a client whose 256-message buffer fills is disconnected.

**Client concurrency.** The network reader goroutine only queues messages on `client.RecvChan`. `Game.Update` drains the queue (`handleMessages`), so game state is only touched from the Ebiten loop. Outbound, the main menu sends server, username and password on `mm.Connect`, chat sends on `chat.SendChan`, and the player sends move requests on `Player.SendChan`, which is buffered and sent without blocking. Goroutines forward all of these into `client.SendChan`, and `connectToServer` writes them to the socket.

## Building clients for playing

- **Mac app on the Desktop.** `~/Desktop/Islanders.app` wraps the client: `Contents/MacOS/Islanders` is a shell script that `cd`s to `~/Library/Application Support/Islanders` (so `imgui.ini` can be written) and runs `Contents/MacOS/islanders-client`, built with `go build -o … ./client/`; `Contents/Info.plist` names it. After rebuilding, re-sign it with `codesign --force --deep -s - ~/Desktop/Islanders.app`.
- **Matching the live server.** To build a client for what's deployed while a branch has unmerged changes, check out the deployed commit (`gh run list --branch master --workflow server.yml` shows it) in a temporary `git worktree` and build there.
- **Windows.** `make build-client-windows`, zipped to `~/Desktop/Islanders-windows.zip`, or the CI artifact.
- **Local testing.** `./bin/server -addr 127.0.0.1:8285 -dev`, then **Play locally**. `-dev` allows dev tools: **F12** in the client opens a Dev window to set the game speed (1×–20×, `World.speed` world ticks per real tick; action timings sent to the client are divided by it so bars stay in real time). The production container runs without `-dev`, so the live server refuses dev commands. A new server or client must be paired: protocol changes mean an old client can't play a new server and vice versa.

## Known pitfalls

- **No persistence.** Accounts, positions and everything else live in server memory, and every deploy wipes them.
- **Older clients** still send `UpdateMessage` with their own position; the server ignores it.
- **imgui-go v4.7.0 leaves out some APIs** (`BeginDisabled`, `TextColored`). Use the helpers in `client/gui/actions.go`: `button(label, enabled)` and `dimmed(text)`. `ProgressBar` overlay text follows the fill; use `centredBar` (`client/gui/skills.go`).
- **Test memory.** Run the server tests one `go test` at a time; two `-race` runs at once stalled the laptop. A normal run peaks around 30 MB (80 MB with `-race`); far more means a runaway test. `testSession` has a large buffer, and `drain` stops at a closed session. A full buffer closes a session, and reading a closed channel in a loop once ate 15 GB. When adding long-running tests, size `runUntil` limits from the timing constants (`ticks(swingTime)`, `walkTicks`) rather than fixed numbers, so tuning speeds doesn't break them.
- **Combat is random.** Tests that fight use strong characters or loop until an outcome; run combat tests with `-count` to check for flakiness after changing them.
- **The island is fixed by `worldSeed`.** Any change to world generation, even adding a placement step, reshuffles later random choices and moves things. The worldgen tests check the properties that matter (reachability, counts, tiers), not exact positions.
